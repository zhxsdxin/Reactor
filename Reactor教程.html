一、前置知识：三个概念，五分钟搞懂

1.1 阻塞 I/O vs 非阻塞 I/O

阻塞 read：就像你打电话给客服，客服说"请稍等"，你拿着电话啥也不能干，只能听等待音乐。

int n = read(fd, buf, 1024);  // 没数据就一直卡在这

非阻塞 read：就像你去餐厅取号，服务员说"还没到你，先去逛逛"，你可以去干别的事，叫号了再回来。

int n = read(fd, buf, 1024);  // fd 已被设为 O_NONBLOCK
// n = -1, errno = EAGAIN  →  "现在没数据，你过会儿再来"

💡 关键：这个项目里所有 socket 都是非阻塞的。这样 Reactor 一个线程就能同时管理成千上万个连接，不会被任何一个连住。

1.2 epoll 是什么

epoll 是 Linux 内核提供的一个"监控告警系统"。你告诉内核"帮我盯着这 10 个 socket"，就可以睡觉了。当任何一个有动静时，内核把你叫醒："喂，3 号房间有客人！"

int epfd = epoll_create1(0);                       // 建一个监控中心
epoll_ctl(epfd, ADD, fd, &event);                 // "帮我盯着 fd"
int n = epoll_wait(epfd, events, 1024, timeout);   // 睡觉，等告警
// 醒来后 events 数组里就是有动静的 fd 列表

epoll vs select：select 像保安挨个房间敲门检查，epoll 是每个房间有按钮，按了保安才知道。一万个房间，select 得敲一万次门，epoll 只去有按钮的房间。

1.3 Reactor 模式 = 死循环 + epoll + 回调表

一句话：Reactor 就是一个调度员。它坐在那等事件（epoll_wait），事件来了查表（fd → Handler），找到对应的人去处理（调回调函数）。做完继续等下一轮。

┌───────────┐
│   epoll   │  内核说："fd=5 可读了！"
└─────┬─────┘
      │ 就绪事件列表
┌─────▼─────┐
│  Reactor  │  查表：fd=5 → SockHandler
│ (调度员)  │  调 SockHandler::handle_read()
└─────┬─────┘
      │ 回调
┌─────▼─────┐
│  Handler  │  读数据 → Echo 回去
└───────────┘

五、逐个文件详解

5.1 include/event_handler.h

作用：定义所有 Handler 必须遵守的"合同"——四个纯虚函数。

enum EventType : uint32_t {
    EVENT_READABLE  = 0x01,   // 位掩码位0: 可读
    EVENT_WRITABLE  = 0x02,   // 位掩码位1: 可写
    EVENT_ERROR     = 0x04,   // 位掩码位2: 错误
};  // 用位掩码, 可以组合: 可读|可写 = 0x03

class EventHandler {
    virtual Handle get_handle() const = 0;   // "你的工号是多少?"
    virtual void handle_read() = 0;          // "有客人来了, 去接待"
    virtual void handle_write() = 0;         // "可以送餐了"
    virtual void handle_error() = 0;         // "出事故了"
    virtual void handle_close() = 0;         // "下班了, 收拾东西"
};

5.2 include/event_demultiplexer.h

作用：定义多路分解器的四个操作，epoll 版和 select 版都要实现。

class EventDemultiplexer {
    virtual int  wait_event(...) = 0;  // "看看谁有动静?"
    virtual bool regist(...)    = 0;   // "帮我把这个人加入监控"
    virtual bool remove(...)    = 0;   // "这个人不用盯了"
    virtual bool modify(...)    = 0;   // "这个人换班了, 改一下监控项"
};

struct ReadyEvent {
    Handle handle;     // 哪个 fd 就绪了
    uint32_t events;   // 就绪的事件类型(可读/可写/错误)
};

七、面试/答辩高频问题

Q1: "从客户端发来 hello 到回显，经过了哪些函数？"

epoll_wait → wait_and_dispatch(reactor_impl.cpp:78) → handle_read(sock_handler.cpp:44) → read() → submit线程池 → pending_tasks_++ 线程池: 写write_buffer_ → pending_tasks_-- → modify_handler(可写) → handle_write(sock_handler.cpp:106) → write() 发回客户端

Q2: "EpollDemultiplexer 里为什么要 event_to_epoll / epoll_to_event 转换？"

隔离层。我们的 EVENT_READABLE 和内核的 EPOLLIN 数值不同，转换函数把它们隔开。将来换 kqueue 时只改这两个函数。

Q3: "sock_fd_ 为什么用 std::atomic？"

事件循环线程在 handle_close 里写 sock_fd_ = -1，线程池 worker 同时读 sock_fd_。两个线程无保护地访问同一个变量 = C++ 的 undefined behavior。atomic 加 exchange 保证安全。

Q4: "handle_close 为什么用 exchange 而不是直接 = ？"

Handle fd = sock_fd_.exchange(INVALID_HANDLE);  // 原子"读+写"

如果两个线程同时调 handle_close：第一个拿到 fd=7 去 close，第二个拿到的是 -1（已被第一个写入了），跳过。不用 exchange 的话两个线程都拿到 7，都去 close(7)，第二次 close 未定义行为。

Q5: "优雅关闭和直接 close 有什么区别？"

close()shutdown(SHUT_WR) + close()
没发完的数据直接丢弃等发完再关
TCP 层面可能发 RST（粗暴）发 FIN（优雅四次挥手）
本项目的触发场景handle_error 等异常客户端正常断开（read 返回 0）

Q6: "水平触发(LT)和边缘触发(ET)？你这个用哪个？"

本项目用 LT（水平触发，默认）。LT 是"还有数据就会反复通知"，ET 是"只通知一次，你读到 EAGAIN 为止"。LT 更安全简单，读循环到 EAGAIN 就能完整处理。
