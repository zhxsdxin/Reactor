二、核心概念 · 大白话版

2.1 什么是 Reactor？为什么不用"一个连接一个线程"？

传统的多线程服务器：每来一个客户端连接，就 fork 一个线程去伺候它。这个线程就一直阻塞在 read() 上等数据。1 万个连接 = 1 万个线程，上下文切换就能把 CPU 榨干。

Reactor 的思路是：一个线程管所有连接。操作系统（epoll）帮我盯着所有 socket，哪个有动静了就告诉我，我去处理。就好比你是一个餐厅前台，不用给每个客人配一个服务员——你只需要盯着门口（epoll），谁举手（socket 可读）你才过去。

2.2 epoll 到底比 select 强在哪？

对比维度selectepoll
fd 数量上限默认 1024（FD_SETSIZE）理论上无上限，只受系统内存限制
查找就绪 fdO(n) 遍历所有 fd，不管有没有事件O(1) 精确返回就绪的 fd 列表
注册机制每次 select 都要把整个 fd_set 从用户态拷到内核态epoll_ctl 一次注册，内核用红黑树维护，之后增量更新
触发方式只有水平触发（LT）支持 LT 和 ET（边沿触发）

打个比方：select 就像你去教室点名——不管学生到没到齐，你得把 50 个人名字全念一遍才知道谁没来。epoll 就像教室门上有个人脸识别——谁进来了、谁出去了，直接告诉你。

2.3 Reactor 的四大角色

角色比喻在本项目里是谁
Reactor调度中心（总指挥）Reactor + ReactorImplementation
EventDemultiplexer事件侦察兵（盯着内核的"眼睛"）EpollDemultiplexer 或 SelectDemultiplexer
EventHandler具体干活的（服务员的行动手册）ListenHandler（门童）、SockHandler（服务员）
Acceptor接客的门童ListenHandler — 只负责 accept 新连接

2.4 水平触发(LT) vs 边沿触发(ET)

水平触发 LT（默认）：只要 socket 缓冲区还有数据没读完，epoll 就会反复通知你"可读"。好处是编程简单，不怕漏数据；坏处是可能多次触发。

边沿触发 ET：只在状态变化时通知一次（从"没数据"变为"有数据"）。好处是高效，只通知一次；坏处是你必须一次性把数据读完，不然就丢数据了。

我代码里默认用 LT 模式，配合 while 循环 + 非阻塞 read，读到 EAGAIN 为止——这样 LT 也能达到 ET 的效果：一次通知读完所有数据。

2.5 阻塞 I/O vs 非阻塞 I/O

阻塞 read：如果 socket 没数据，read() 就卡住不动了，整个线程都等着。Reactor 模式下 = 自杀。

非阻塞 read：没数据时 read() 立刻返回 -1，errno = EAGAIN。你可以接着去处理其他 fd。核心代码就两行：fcntl(fd, F_GETFL) → flags | O_NONBLOCK → fcntl(fd, F_SETFL)

三、逐文件讲解（按"为什么要这么写"的思路）

3.1 event_handler.h — 定规矩的"合同"

设计动机：Reactor 模式的核心是"面向接口编程，不面向具体实现"。Reactor 只知道 EventHandler 这个抽象类型，不知道具体是 ListenHandler 还是 SockHandler。这样将来加一个 HttpHandler、WebSocketHandler，Reactor 代码一行不用改。

// 位掩码设计：用一个 uint32_t 表示多种事件的组合
enum EventType : uint32_t {
    EVENT_READABLE  = 0x01,   // 0000 0001
    EVENT_WRITABLE  = 0x02,   // 0000 0010
    EVENT_ERROR     = 0x04,   // 0000 0100
};
// "既要读又要写" = 0x01 | 0x02 = 0x03
// 判断是否可读：events_ & EVENT_READABLE → 不为 0 就是可读

为什么要用位掩码？因为一个 fd 可能同时关心多种事件（比如既想读又想写）。如果用 enum 只能表示一种状态，用位掩码可以用一个整数表示任意组合。epoll 底层也是这么干的（EPOLLIN=0x001, EPOLLOUT=0x004）。

3.2 event_demultiplexer.h — 多路分解的抽象

设计动机：把"等待事件"这个操作抽象成接口，底层可以是 epoll 也可以是 select。切换只需改一行条件编译，Reactor 完全不用动。

struct ReadyEvent {
    Handle handle;   // 哪个 fd 就绪了
    uint32_t events; // 发生了什么事件（可读/可写/错误）
};

wait_event 返回一个 vector<ReadyEvent>，不管底层是 epoll 还是 select，调用者看到的数据结构完全一样。

3.3 epoll_demultiplexer.cpp — epoll 封装（核心）

关键实现细节：

// 构造函数：一次分配，反复使用（符合 PDF "不可滥用内存分配" 要求）
EpollDemultiplexer::EpollDemultiplexer() : evs_(MAX_EVENTS) {
    epoll_fd_ = epoll_create1(0);  // 创建一个 epoll 实例
}

// 事件类型转换：我们的事件 → epoll 的事件
static uint32_t event_to_epoll(uint32_t evt) {
    uint32_t ep = 0;
    if (evt & EVENT_READABLE)  ep |= EPOLLIN;
    if (evt & EVENT_WRITABLE)  ep |= EPOLLOUT;
    if (evt & EVENT_ET)        ep |= EPOLLET;
    return ep;
}

为什么要做类型转换？用我们自己的 EventType 枚举而不是直接暴露 epoll 常量，这样换 select 时不用改上层代码。这是典型的"隔离变化"思想。select 那边也有对应的宏 FD_SET/FD_CLR。

3.4 select_demultiplexer.cpp — select 封装（加分）

select 和 epoll 的核心区别体现在代码里：

// select 不告诉哪些 fd 就绪，得自己遍历
for (Handle fd = 0; fd <= max_fd_ && (int)ready_events.size() < nfds; ++fd) {
    if (FD_ISSET(fd, &read_fds))   evt |= EVENT_READABLE;
    if (FD_ISSET(fd, &write_fds))  evt |= EVENT_WRITABLE;
    // ...
}

三个 fd_set（read_set_ / write_set_ / except_set_）+ FD_ZERO / FD_SET / FD_CLR 宏。注意 select 会修改传入的 fd_set，所以 wait_event 里必须用副本（第 19-21 行）。

remove 的特殊处理：删掉一个 fd 后，如果它恰好是 max_fd_，需要往回找新的最大值（第 77-84 行）。不更新的话 select 会多扫描一堆空 fd，浪费 CPU。

3.5 reactor_impl.cpp — 事件循环的心脏

wait_and_dispatch — 这是整个 Reactor 最核心的函数，只有 30 行：

int ReactorImplementation::wait_and_dispatch(int timeout_ms)
{
    // ① 等待事件（底层调 epoll_wait / select）
    int n = demux_->wait_event(ready_events, timeout_ms);

    // ② 遍历每一个就绪的 fd
    for (const auto& re : ready_events) {
        handler = handlers_[re.handle];   // fd → Handler 查表

        // ③ 先处理错误/挂断（优先级最高）
        if (re.events & (EVENT_ERROR | EVENT_HANGUP | EVENT_RDHUP)) {
            handler->handle_error();
            handler->handle_close();
            continue;  // 出错了就不处理读写
        }
        // ④ 正常情况：读了写
        if (re.events & EVENT_READABLE)   handler->handle_read();
        if (re.events & EVENT_WRITABLE)   handler->handle_write();
    }
}

关键设计决策——为什么要持锁查表、释放锁后再调回调？因为 handle_read 里可能调用 remove_handler（客户端断开时），remove_handler 也要拿同一把互斥锁。如果持锁调回调 → 死锁。所以代码里用花括号限制锁的作用域：{ lock_guard lock(mutex_); handler = handlers_[fd]; } → 锁在这里释放 → 然后才调 handler->handle_read()。

3.6 reactor.cpp — 单例 + 事件循环主循环

为什么 Reactor 要用单例？一个进程里通常只有一个事件循环。不能让两个 Reactor 各自搞一个 epoll_wait，会乱套。

Reactor& Reactor::get_instance() {
    static Reactor instance;  // C++11 保证线程安全，只构造一次
    return instance;
}

event_loop 的三件事（每一轮循环）：

while (is_running()) {
    int timeout = timer_heap_->get_next_timeout_ms(); // ① 算超时
    impl_->wait_and_dispatch(timeout);                // ② 等事件+分发
    timer_heap_->tick();                              // ③ 触发到期定时器
}

超时时间的精妙之处：epoll_wait 的超时取"最近一个定时器到期时间"和"默认 100ms"的最小值。这样既能保证定时器准时触发，又不会在没事件时空转。如果定时器比默认超时还远，就用默认超时——确保 loop 至少每 100ms 检查一次 running_ 标志，能及时响应 Ctrl+C。

3.7 listen_handler.cpp — 门童（Acceptor）

start() 就是标准 TCP 服务端五步：

socket()     → 创建 socket，拿到 fd
setsockopt   → SO_REUSEADDR，允许端口复用（防止重启时 "Address in use"）
fcntl        → O_NONBLOCK，设为非阻塞
bind()       → 绑定到 0.0.0.0:8080
listen()     → 开始监听，SOMAXCONN 是内核允许的最大 backlog

handle_read 的精髓：while accept 到底

void ListenHandler::handle_read() {
    while (true) {
        int client_fd = accept(listen_fd_, ...);
        if (client_fd < 0) {
            if (errno == EAGAIN || errno == EWOULDBLOCK) break; // 没新连接了
            // 真正的错误...
            break;
        }
        // 为新连接创建 Handler 并注册
        auto sock = std::make_shared<SockHandler>(client_fd);
        sock->set_nonblocking();
        Reactor::get_instance().register_handler(sock, EVENT_READABLE);
    }
}

为什么是 while accept？和 handle_read 里 while read 同理。可能在 epoll 通知我们"监听 fd 可读"和实际执行 accept 之间，又有好几个新连接进来了。一次 accept 只取一个，剩下的会留在内核的 accept 队列里等下一次通知——多浪费一轮 epoll_wait。while accept 一次全取出来。

3.8 sock_handler.cpp — Echo 服务员（最复杂的一个）

前面 index.html 里已经逐行拆解过了，这里讲关键的四个设计决策：

决策一：为什么 handle_read 要把数据交给线程池处理？

PDF 加分项要求："handleRead 只做数据读取，然后把数据交给线程池去做耗时处理"。

虽然 Echo 的处理很简单（原样返回），但设计上留了这个口子——线程池的 lambda 里可以随便加逻辑（JSON 解析、加密解密、数据库查询），都不会阻塞 Reactor 主循环。这体现了 IO 和业务处理分离的思想。

决策二：为什么要用 shared_from_this？

auto self = shared_from_this();
Reactor::get_instance().get_thread_pool().submit(
    [self, data = std::move(data)]() {
        // self 保证了 SockHandler 在 lambda 执行期间不会被析构
    });

线程池的 lambda 可能在未来任意时刻执行。如果客户端已经断开、SockHandler 已经被删了，lambda 里访问 self 就是野指针。shared_ptr 引用计数保证对象在 lambda 执行期间还活着。

决策三：读缓冲和写缓冲为什么设计不一样？

read_buffer_ — 固定大小 char[1024]，栈上分配，每次 read 覆盖写入。因为每次读的数据量不确定但最大 1024 字节。

write_buffer_ — vector<char>，动态扩容。因为网络拥堵时可能要暂存多次读到的数据，暂时发不出去要堆积——固定大小就不够用了。

决策四：写完为什么要恢复只读？

// 写完所有数据后
Reactor::get_instance().modify_handler(sock_fd_, EVENT_READABLE);

如果不改回来，每次 epoll_wait 都会报"可写"（因为 socket 发送缓冲区一直有空间），导致 handle_write 被频繁空转调用——白白浪费 CPU。这就是 Reactor 里"动态修改关心事件"的典型用法。

3.9 thread_pool.cpp — 线程池

经典的生产者-消费者模型：

// 生产者（Reactor 线程）
pool.submit(task);       // 锁 → 入队 → 解锁 → notify_one()

// 消费者（Worker 线程）
cond_.wait(lock, []{ return !running_ || !tasks_.empty(); });
task = tasks_.front(); tasks_.pop();
lock.unlock();           // 执行前释放锁！
task();                  // 不持锁执行

为什么 task() 执行前要释放锁？如果持锁执行任务，其他 worker 线程就取不到锁、没法从队列取任务，等于把多线程退化成单线程了。而且 task 里可能调 submit()（嵌套投递），持锁 + 再拿锁 = 死锁。

3.10 timer.cpp — 定时器（小顶堆）

用 std::priority_queue + std::greater 实现，堆顶是最快到期的。

add_timer(5000, []{ printf("每5秒打印一次"); })  →  压入堆
get_next_timeout_ms()  →  堆顶.deadline - now  →  作为 epoll_wait 超时
tick()                 →  pop 所有到期的定时器并执行回调

main.cpp 里实现了一个"周期性定时器"的小技巧：回调里调 add_periodic_timer() 把自己重新注册，实现每 5 秒触发一次。

五、关键设计决策和"为什么"

设计决策怎么做的为什么这么做
单例 Reactor static Reactor instance;
C++11 局部静态变量		 一个进程只需要一个事件循环。两个 Reactor 各管各的 epoll → 事件可能丢给错误的循环 → 乱套。C++11 保证多线程环境下只构造一次。
pimpl 模式 Reactor 只暴露接口，具体实现在 ReactorImplementation 里 接口和实现分离。如果要加新功能（比如多 epoll 实例），改 ReactorImplementation 就行，Reactor 接口不用动。
条件编译切换 epoll/select #ifdef USE_SELECT ... #else ... #endif PDF 要求"使用 epoll"，但 select 作为加分项。两者实现同一个接口，上层代码完全不用改。
while 循环读到 EAGAIN handle_read 里 while(true){ read()... if EAGAIN break } LT 模式下，不一次读完就会反复触发 epoll_wait。一次读到底，减少系统调用次数。
非阻塞 socket fcntl(fd, F_SETFL, flags | O_NONBLOCK) 阻塞 read 会卡住整个线程。Reactor 的一个线程管所有连接 = 绝对不能有任何地方阻塞。
智能指针管理生命周期 shared_ptr + shared_from_this 避免手动 delete 导致的内存泄漏或野指针。线程池的 lambda 持有 shared_ptr，保证对象在异步执行期间不被销毁。
锁的作用域最小化 { lock_guard lock(m); ... }
锁在花括号结束时释放		 持锁调用回调 = 死锁风险。锁只保护数据结构（map、vector），不保护业务逻辑。
写完后恢复只读 modify_handler(fd, READABLE) 否则每次 epoll_wait 都报可写（空转）。只在真正有数据要发的时候才注册可写事件。
定时器超时联动 epoll_wait timeout = min(定时器超时, 默认100ms) 既不空转 CPU（没事件时不忙等），又能准时触发定时器，还能及时响应 Ctrl+C。

六、答辩 / 助教常问 FAQ（重点看！）

这些问题是助教最可能问的，提前想好怎么回答

Q1: Reactor 和 Proactor 的区别是什么？
答：Reactor 是同步非阻塞 I/O——内核通知你"可读了"，你自己调 read() 去读数据。Proactor 是异步 I/O——你告诉内核"帮我读"，内核读完了通知你"数据在这"。
打个比方：Reactor 是快递员打电话说"快递到楼下了，下来拿"；Proactor 是快递员直接放到你家门口说"到了"。
Linux 主流用 Reactor + epoll，Windows 主流用 Proactor + IOCP（我们后来的远控项目会用到）。
Q2: 为什么 epoll 比 select 快？
答：三个原因：
① fd 数量：select 硬上限 1024，epoll 理论上无上限；
② 查找就绪：select 需要 O(n) 遍历所有 fd，epoll 直接 O(1) 返回就绪 fd 列表（存在内核的红黑树 + 就绪链表里）；
③ 注册开销：select 每次调用都要把整个 fd_set 拷进内核，epoll 只需注册一次（epoll_ctl），内核记住后用事件通知；
④ 数据结构：epoll 内核用红黑树存所有注册的 fd，用双向链表存就绪的 fd。插入/删除/查找都是 O(log n)。
Q3: ET 和 LT 有什么区别？你的代码为什么用 LT？
答：LT（水平触发）：只要数据没读完就一直通知；ET（边沿触发）：只在"没数据→有数据"时通知一次。
我用 LT 是因为编程更安全——不容易漏数据。但用 while 循环读到 EAGAIN 为止，效果和 ET 一样（一次通知读完所有数据）。代码里 EventType 枚举留了 EVENT_ET=0x20 的标志位，传给 epoll 时加上 EPOLLET 就能切 ET 模式。
Q4: handle_read 里为什么要把数据交给线程池而不是直接处理？
答：这是 PDF 加分项要求的"handleRead 只做数据读取，然后把数据交给线程池去做耗时处理"。
核心思想是IO 和业务处理分离：Reactor 线程（IO 线程）只负责快速读写 socket，耗时操作（JSON 解析、数据库查询等）丢给线程池异步执行。这样 IO 线程不会被阻塞，能保持对其他连接的高响应性。
具体实现：handle_read 读数据 → 投递 lambda 到线程池 → handle_read 返回（耗时约几微秒）。线程池 Worker 处理完 → modify_handler 通知 Reactor "可以写了" → 下次 epoll 触发 handle_write。
Q5: 线程池怎么保证线程安全？
答：三处需要加锁：
① 任务队列（thread_pool.cpp）：mutex + condition_variable，生产者和多个消费者之间互斥；
② 写缓冲区（sock_handler.cpp）：write_mutex_，因为线程池 Worker 和 Reactor 线程可能同时操作 write_buffer_；
③ Handler 映射表（reactor_impl.cpp）：mutex_，因为 register_handler 和 wait_and_dispatch 在不同线程可能同时访问。
特别注意：锁只保护数据结构，回调函数在释放锁之后执行——避免持锁调回调导致的死锁。
Q6: 你这里用的是单 Reactor 还是主从 Reactor？
答：我实现的是单 Reactor + 线程池模式。一个 Reactor 线程负责所有 IO（accept + 读写），4 个工作线程负责业务处理。
如果要升级成主从 Reactor：主 Reactor 只处理 listen fd（accept），从 Reactor（多个）各自管理一部分连接的读写。这样可以利用多核 CPU 并行处理 IO，适合更高并发的场景。这也是 Netty / Nginx 等生产级框架的做法。
Q7: 定时器是怎么和事件循环联动的？
答：小顶堆（priority_queue）的堆顶是最快到期的定时器。每一轮事件循环：
① get_next_timeout_ms() 算堆顶还有多久到期；
② 取 min(定时器超时, 默认 100ms) 作为 epoll_wait 的超时参数；
③ epoll_wait 返回后（可能是超时返回，也可能是事件到达），调用 tick() 检查并执行所有到期的定时器。
这样定时器不会错过（超时 <= 最早定时器），也不会空转 CPU（没事件时最多等 100ms）。
Q8: 如果客户端发送的数据超过 1024 字节怎么办？
答：因为用的是水平触发 + while 循环读完，多次 read 会拼接。但当前 Echo 实现每次 read 到数据就单独处理（丢线程池 → 写回）。如果一帧数据超过 1024 字节会被拆成多次 handle_read 调用，每次独立 echo 回去。
正确的做法是在应用层做"粘包/拆包"处理：读到的数据先放缓冲区，按协议边界（如长度前缀、分隔符）来拆分消息帧。这在生产级代码里是必须的，但我这个 Demo 没做——因为考核重点是 Reactor 架构，不是协议设计。
Q9: 为什么 listen fd 和 client fd 都要设非阻塞？
答：listen fd 设非阻塞是因为：在极少数情况下（如连接在 accept 前被 RST 重置），即便是 select/epoll 说可读，accept 也可能阻塞。设非阻塞后 accept 返回 EAGAIN，我们 while 循环里 break 就好。
client fd 设非阻塞是必须的：否则 read 没数据时整个线程卡住，其他 9999 个连接全部无法处理。
Q10: 代码里用了哪些 C++17 特性？
答：① std::make_unique（C++14 开始有，C++17 更成熟）管理 exclusive ownership；
② lambda 表达式 + 移动捕获（[data = std::move(data)]）避免不必要拷贝；
③ auto 类型推导简化代码；
④ std::chrono 用于定时器的精确计时；
⑤ std::atomic 用于线程安全的标志位；
⑥ = default / = delete 显式声明特殊成员函数。
